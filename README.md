# Pipupi — `traffic-podryad-pro`

**Pipupi** — платформа автоматизации маркетинга, которую мы строим **сначала для себя** (internal-first), а затем открываем как продукт для клиентов.

Смысл продукта в одной фразе: **превратить исследование поисковых запросов в проверяемый поток заявок**, где каждый лид можно проследить назад до конкретной статьи, кластера тем, ключевого запроса, продукта и региона.

> **Статус репозитория: Wave 4 в работе (4a рантайм, 4b авторизация).**
> Есть Bun-воркспейс, контракты, схема Prisma с первой миграцией, рантайм backend
> (env-предохранители, health, durable outbox, вход и роли), локальная база в Docker
> Compose, проверки границ архитектуры и CI. Продуктовых модулей, провайдеров и
> поверхностей пока нет. См. раздел [«Что будет реализовано дальше»](#что-будет-реализовано-дальше).

## Четыре линии услуг

Платформа принимает **service requests** — заявки на работу. Сейчас их заводим мы сами, позже это станет клиентским интерфейсом. Линий четыре, и в MVP они исполняются по-разному:

| Линия | Что это | Поведение в MVP |
| --- | --- | --- |
| `seo_content` | SEO-контент и органический трафик | **Полное исполнение** сквозного среза |
| `b2b_outreach` | Планирование B2B-коммуникации | Только приём заявки и планирование |
| `telegram_marketing` | Планирование Telegram-маркетинга | Только приём заявки и планирование |
| `complex_package` | Комплексный пакет | Декомпозируется на дочерние заявки; исполняется только SEO-часть |

`b2b_outreach` и `telegram_marketing` завершаются в состоянии **`planned_awaiting_capability`**. Это **намеренное терминальное состояние, а не ошибка**: план готов и одобрен, а возможности исполнения в продукте сознательно нет. Условия её появления описаны в [docs/ROADMAP_OUTREACH_TELEGRAM.md](docs/ROADMAP_OUTREACH_TELEGRAM.md).

## Текущий MVP

MVP — это **один вертикальный срез, доведённый до конца**, а не набор наполовину готовых модулей:

```
service request (seo_content)
  → CSV-импорт ключевых запросов
  → нормализация и дедупликация
  → привязка к продукту и региону
  → классификация интента
  → кластеризация тем
  → бриф (DeepSeek)
  → черновик статьи (DeepSeek)
  → правка человеком
  → проверка фактов, SEO и CTA
  → одобрение одним человеком, привязанное к content hash
  → публикация на Astro-сайт
  → CTA-форма запроса цены
  → тестовый лид
  → атрибуция: лид → статья → кластер → ключ → продукт → регион
  → экран воронки в приложении
```

Критерий готовности: на проде существует опубликованная статья, пришедший через её CTA лид и запись атрибуции, связывающая их, — и всё это воспроизводится одним E2E-тестом.

Пошаговое описание конвейера — в [docs/CONTENT_PIPELINE.md](docs/CONTENT_PIPELINE.md).

### Чего в MVP нет — намеренно

Отправка исходящих сообщений · хранение контактов третьих лиц · холодная email-рассылка · массовые сообщения в Telegram · приглашения в Telegram · MTProto · автоматизация пользовательских аккаунтов · сбор участников чужих каналов · обход капчи · обход банов · мультиарендность · биллинг и платежи · нативное мобильное приложение · внешние счётчики аналитики · ISR и SSR · n8n · A/B-тестирование · совместное редактирование в реальном времени.

Это не «ещё не успели». Часть пунктов не появится никогда — см. [docs/COMPLIANCE.md](docs/COMPLIANCE.md).

## Локальная разработка

| Компонент | Инструмент |
| --- | --- |
| Runtime | Bun, версия запинена в `.bun-version` и в `packageManager` |
| Монорепозиторий | Bun workspaces: `backend`, `webapp`, `website`, `packages/*` |
| Локальная БД | Docker Compose, `postgres:18-alpine`, порт `54329`; отдельный тестовый сервис на `54330` |
| Проверки | `architecture:check`, `check:secrets`, `check:agent-docs`, `check:repo-env`, `bun test` |

```bash
bun install                 # связывает воркспейсы и ставит зависимости

bun run check               # все репозиторные проверки разом
bun run architecture:check  # границы модулей, AC-1..AC-3
bun run test                # фикстурные тесты проверок, контракты, схема, unit-тесты backend
bun run test:integration    # backend против Docker PostgreSQL (outbox, health, сиды)
bun run compose:config      # валидация docker-compose.yml без запуска демона

cp backend/.env.example backend/.env
bun run db:start            # локальный PostgreSQL
bun run db:status
bun run db:stop
```

Подробности — [docs/LOCAL_DATABASE.md](docs/LOCAL_DATABASE.md), тесты — [docs/TESTING.md](docs/TESTING.md).

`pgvector` локально **не включён**: базовый образ `postgres:18-alpine` его не содержит, ничему в репозитории он пока не нужен, а продакшн-ворота не пройдены. Обоснование — [docs/LOCAL_DATABASE.md §2.1](docs/LOCAL_DATABASE.md), ворота — [docs/DEPLOYMENT.md §3](docs/DEPLOYMENT.md).

Секреты живут только в `.env`-файлах, которые не попадают в Git. В репозитории — **только** `backend/.env.example` с плейсхолдерами; `bun run check:secrets` блокирует появление настоящих.

## Архитектурное направление

**Модульный монолит.** Один backend-кодовый базис, одна база данных, общие контракты, явные границы контекстов внутри репозитория.

| Слой | Решение |
| --- | --- |
| Runtime | Bun |
| Backend | Hono, модули `transport → application → domain → infrastructure` |
| Данные | Prisma + PostgreSQL |
| Публичный сайт | Astro SSG |
| Приложение | React CSR |
| Контракты | Общие Zod-схемы в `packages/contracts` — единственный источник правды для API |
| Долговечная работа | Durable outbox в PostgreSQL |
| Best-effort работа | Отдельный механизм фоновых задач внутри запроса |
| Периодическая работа | Реестр задач + сменные runner'ы (cron / scheduler / worker) |
| Внешние сервисы | Только через ports и adapters в `backend/src/providers/**` |
| Локальная БД | Docker Compose |
| Продакшн | Yandex Cloud — единственная целевая площадка |

**Чего мы не вводим:** микросервисы, Kubernetes, Redis, Valkey, Kafka, RabbitMQ, Elasticsearch и любой внешний брокер. Не «пока не вводим» — не вводим до тех пор, пока **записанное измерение** не докажет, что текущий подход упёрся в предел. Правило и порядок такого решения — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

Из шаблона взяты структура монорепозитория, разделение поверхностей, дизайн фоновых задач, подход к контрактам, конвенции тестирования и инструкции для агентов. **[alexdmitrievi/Podryad_PRO](https://github.com/alexdmitrievi/Podryad_PRO)** используется **исключительно как справочник по предметной области**: какие поля нужны лиду, как выглядит UTM-атрибуция, как устроен приём заявок. Из него **не копируются**: архитектура, n8n-воркфлоу, MTProto-инвайтер, автоматизация пользовательских аккаунтов Telegram, история сырых миграций, аутентификация по `ADMIN_PIN`, секреты и продакшн-доступы. У репозитория нет объявленной лицензии, поэтому заимствование кода из него исключено.
