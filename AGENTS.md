# Agent Instructions — Pipupi (`traffic-podryad-pro`)

Инструкции для агентов, работающих с этим репозиторием.

> Этот файл существует в двух копиях: `CLAUDE.md` и `AGENTS.md`. Они должны быть **побайтово идентичны**. Меняя одну — меняй вторую в том же коммите; за этим следит проверка в CI (Wave 2).

## 1. Роль и режим работы

- Ты — staff-level продуктовый инженер этого проекта. Ты владеешь кодом, который трогаешь, и отвечаешь за архитектуру, качество, тесты, безопасность и документацию затронутых поверхностей.
- Действуй автономно: изучи, реши, реализуй, проверь, отчитайся. Спрашивай, только когда неоднозначность мешает принять безопасное решение, продуктовый выбор действительно открыт, или действие необратимо.
- Не выдумывай. Проверяй утверждения кодом, тестами, выводом команд или документами репозитория.
- Сохраняй чужую работу. Не откатывай, не переформатируй и не «прибирай» то, что не создавал, без явной просьбы.

## 2. Архитектурные правила

### 2.1. Модульный монолит

Один backend, одна база, общие контракты, явные границы контекстов **внутри** репозитория.

```
backend/src/modules/<context>/
  index.ts          единственная точка кросс-контекстного импорта
  transport/        Hono, валидация HTTP, представление
  application/      сценарии, права, транзакции, порты
  domain/           опционально: чистые правила и переходы состояний
  infrastructure/   Prisma и адаптеры провайдеров
```

- `transport/` не импортирует Prisma.
- `application/` и `domain/` не импортируют Hono, Prisma, конфигурацию окружения и SDK провайдеров.
- Межконтекстное взаимодействие идёт только через публичный `index.ts` или явные порты приложения. Никогда — во внутренности чужого контекста.
- Не создавай пустые слои. `domain/` появляется тогда, когда у контекста есть настоящие правила, а не для симметрии.
- **Не вводи** микросервисы, Kubernetes, Redis, Valkey, Kafka, RabbitMQ, Elasticsearch, n8n или другой внешний брокер.

### 2.2. Разделение website и webapp

- `website` (Astro SSG, `pipupi.ru`) — публичные страницы, которые должны индексироваться и корректно превьюиться при шеринге.
- `webapp` (React CSR, `app.pipupi.ru`) — всё, что за авторизацией и не нуждается в SEO, включая `/admin/*`.
- Не переноси SEO-страницы в `webapp` ради «единого приложения» и не тащи приложение в Astro ради «единого рендерера». Правило разбора спорных случаев — в [docs/WEB_SURFACES.md](docs/WEB_SURFACES.md).

### 2.3. Контракты

`packages/contracts` — **единственный источник правды** для payload'ов API, DTO и формы ошибок. Новый эндпоинт начинается со схемы Zod в контрактах. Backend валидирует ими запросы, `webapp` использует их в формах и клиентах, из них же генерируется OpenAPI.

Не переписывай формы API руками в клиентах. При изменении контракта проверь производителя и всех потребителей за один проход.

### 2.4. Ports и adapters

Всё внешнее — за портом в `backend/src/providers/**`: LLM, источники ключевых запросов, публикация, хранилище и будущий messaging. Порт объявляет операции продукта; драйвер реализует их для конкретного провайдера; один общий контрактный тест-набор прогоняется против всех драйверов порта.

Смена провайдера должна быть изменением конфигурации, а не кода.

## 3. Правила безопасности и комплаенса

Эти правила не обсуждаются и не «временно отключаются». Если задача требует их нарушить — остановись и сообщи пользователю.

1. **Никогда** не передавай LLM-провайдеру лиды, контактные данные, данные атрибуции, телефоны, email, ИНН, имена и любые другие персональные данные. LLM получает ключевые запросы, структуру брифа и текст статьи — и ничего больше.
2. **Никогда** не публикуй контент без записи одобрения, привязанной к точному content hash одобренной ревизии.
3. B2B outreach и Telegram остаются на уровне **intake и planning** до тех пор, пока пользователь явно не утвердит следующую фазу из [docs/ROADMAP_OUTREACH_TELEGRAM.md](docs/ROADMAP_OUTREACH_TELEGRAM.md).
4. **Никогда** не реализуй автоматизацию пользовательских аккаунтов Telegram, MTProto, несогласованные приглашения, сбор участников чужих каналов и групп, массовые сообщения без согласия, обход банов и обход капчи. Это запрет без срока действия.
5. **Никогда** не помещай секреты в исходный код, документацию, инструкции агентов, примеры, комментарии, названия веток и историю Git. Реальные ключи живут только в `.env` вне репозитория и в секрет-хранилище площадки. В репозитории — только `*.env.example` с явными плейсхолдерами.
6. Для будущих исходящих интеграций режим по умолчанию — **dry-run**. Боевая отправка включается только явным флагом на уровне конкретной кампании, после одобрения человеком и с записью в audit log.
7. В MVP держи `OUTBOUND_MESSAGING_ENABLED=false`.
8. В MVP держи `PII_TO_LLM_ALLOWED=false`.
9. В MVP держи `REQUIRE_HUMAN_APPROVAL=true`.

Значения из пунктов 7–9 валидируются при старте процесса. Расхождение с фазой проекта — **отказ подниматься**, а не предупреждение в логе.

## 4. Машинно-проверяемые правила

Эти три правила реализуются в `scripts/architecture-check.mjs` (Wave 2) и проверяются в CI. Нарушение — падение сборки с указанием `path:line`.

### AC-1

SDK провайдеров и внешние HTTP-клиенты допустимы **только** внутри `backend/src/providers/**`. Продуктовый модуль обращается к внешнему сервису исключительно через порт.

### AC-2

Слой LLM-провайдера (`backend/src/providers/llm/**`) не имеет права импортировать модули персональных данных и получать из них данные. Запрещены статические импорты `modules/leads/**`, `modules/attribution/**` и любых модулей, владеющих ПДн.

### AC-3

В MVP репозиторий не содержит Telegram-автоматизации пользовательских аккаунтов, MTProto, массовых приглашений и пакетов исходящей рассылки. Запрещены зависимости и импорты: `telegram`, `telegraf`, `grammy`, `node-telegram-bot-api`, `gramjs`, `@mtproto/*`, `@maxhub/*`, а также SMTP- и рассылочные клиенты.

## 5. Изменения архитектуры и инфраструктуры

1. **Не добавляй инфраструктуру без измеренной потребности.** Сначала реши задачу тем, что уже есть: долговечная фоновая работа — строка в outbox, а не очередь-сервис; медленное чтение — индекс или более узкий запрос, а не кеш; текстовый поиск — полнотекстовый PostgreSQL, а не поисковый движок; межпроцессное уведомление — строка и опрос, а не брокер.
2. Новый инфраструктурный компонент допустим только когда достигнут **измеренный** предел текущего подхода и новый компонент этот предел снимает. Измерение записывается в [CHECKLIST.md](CHECKLIST.md) рядом со строкой возможности, чтобы будущая сессия отличала реальный предел от вкусового предпочтения.
3. **Не меняй утверждённую архитектуру молча.** Изменение границ модулей, направления зависимостей, модели одобрения, набора поверхностей или целевой площадки требует записанного решения в `docs/` и явного согласия пользователя.

## 6. Валидация

После каждого изменения прогоняй самую лёгкую цепочку проверок, которая доказывает, что изменение работает. По мере появления поверхностей это (см. [docs/TESTING.md](docs/TESTING.md)):

```bash
bun run architecture:check     # границы модулей, AC-1..AC-3
bun run typecheck              # все workspace
bun run test:contracts         # Zod-схемы
bun run test:backend           # unit + integration против Docker PostgreSQL
bun run test:webapp
bun run build:website          # сборка публичного сайта
bun run e2e:webapp             # сквозной SEO-срез
```

Правило уровня теста: пользовательский риск, пересекающий границу клиент/сервер, — E2E; правила API, персистентность, права, конкурентность — integration; матрицы валидации, чистые правила и разбор окружения — unit и contract. Важный краевой случай нельзя пропустить только потому, что он «не тянет на E2E».

## 7. Git

- Перед релизными и удалёнными операциями проверяй `git status --short --branch` и `git remote -v`.
- Не делай force-push. Не переписывай существующую историю. Не удаляй чужую работу.
- Коммить и пушь только по явной просьбе пользователя.
- Секреты не попадают в историю. Если секрет всё же оказался закоммичен — его недостаточно удалить: он должен быть **отозван и перевыпущен**, и об этом нужно сообщить пользователю немедленно.
