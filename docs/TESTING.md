# Тестирование и валидация

Цель этих проверок — не покрытие ради покрытия, а **защита ценного поведения**: сквозного SEO-среза, обязательности одобрения и границ, отделяющих персональные данные от внешних провайдеров.

> Тестов в репозитории пока нет — код появится в Wave 2–4. Этот документ задаёт, как они будут устроены и что обязаны доказывать.

---

## 1. Пирамида

| Уровень | Что проверяет | Что нужно для запуска |
| --- | --- | --- |
| **Unit** | Чистые правила, переходы состояний, нормализация ключей, дедупликация, вычисление хешей, разбор окружения | Ничего |
| **Contract** | Zod-схемы из `packages/contracts`: матрицы валидации, границы, формы ошибок | Ничего |
| **Integration** | API, права, персистентность, конкурентность, доменные правила поверх реальной базы | Docker PostgreSQL |
| **Provider contract** | Один набор тестов против всех драйверов порта | Зависит от драйвера |
| **Architecture** | Границы модулей и правила AC-1…AC-3 | Ничего |
| **E2E** | Сквозной SEO-срез через реальный backend и реальный интерфейс | Docker PostgreSQL + сборка поверхностей |

### Разделение по имени файла

Имя файла определяет раннер — тесты обнаруживаются, а не перечисляются вручную:

| Шаблон имени | Раннер | Требует |
| --- | --- | --- |
| `*.integration.test.ts` | `bun run test:integration` (последовательный прогон файлов в `backend/tests/integration/run.mjs`) | Docker PostgreSQL |
| `*.live.test.ts` | `test:live` | Внешний сервис, запускаемый отдельно |
| `*.test.ts` | `bun test src` | Ничего |

Интеграционные файлы прогоняются **последовательно**, а не параллельно: тесты делят одну
базу, а drain-тесты outbox запускают настоящие циклы захвата, которые в параллельном
прогоне уводили бы строки у других файлов. Конкурентность проверяется внутри тестов
(два дренажа, два воркера), а не между файлами.

Категория `live` существует, чтобы `bun run test` оставался запускаемым на машине без Docker. Live-тест, попавший в unit-набор, падал бы у всех, кто не поднял контейнер, — а красный набор, который все привыкли игнорировать, хуже отсутствующего.

Отдельный тест проверяет, что раннеры остаются взаимодополняющими и ни один файл не выпал из всех наборов.

## 2. Выбор уровня

По умолчанию — **самая высокая полезная поведенческая граница**.

- **E2E**, когда риск виден пользователю и пересекает границу клиент/сервер: сквозной срез, восстановление сессии, важные состояния пустоты и ошибок.
- **Integration**, когда риск в API, правах, персистентности, конкурентности и доменных правилах.
- **Unit и contract**, когда речь о чистых правилах с множеством ветвей, матрицах валидации, разборе окружения и вычислении хешей.

Правило, которое легко нарушить: **важный краевой случай нельзя пропустить только потому, что он «не тянет на E2E».** Выбор integration вместо E2E — это выбор уровня, а не разрешение не проверять. И обратно: исчерпывающие матрицы валидации в E2E не место.

## 3. Полная цепочка валидации

```bash
bun run architecture:check     # границы модулей, AC-1..AC-3
bun run typecheck              # все workspace
bun run test:contracts         # Zod-схемы
bun run test:backend:unit      # backend unit, без Docker
bun run test:integration       # backend против Docker PostgreSQL: outbox, health, сиды
bun run test:webapp
bun run build:website
bun run e2e:webapp
```

Дополнительно в CI:

| Проверка | Что делает |
| --- | --- |
| **Secret scanning** | Grep-gate по паттернам токенов и ключей. Блокирует merge |
| **Migration validation** | Структурная проверка миграций до применения |
| **Website build** | Публичный сайт собирается без ошибок |
| **Lighthouse** | Бюджет производительности и доступности для страницы статьи |
| **CLAUDE.md = AGENTS.md** | Файлы побайтово идентичны |
| **Dependency audit** | Известные уязвимости зависимостей |

## 4. Тесты границ архитектуры

У каждого правила — фикстурные тесты: заведомо нарушающий пример должен приводить к падению, заведомо корректный — к успеху. Правило без такого теста считается ненадёжным: молча переставшая работать проверка хуже отсутствующей.

| Правило | Фикстура-нарушение |
| --- | --- |
| **AC-1** | Импорт SDK провайдера внутри `modules/` вместо `providers/` |
| **AC-2** | Импорт `modules/leads` из `providers/llm/` |
| **AC-3** | Появление зависимости мессенджера в любом `package.json` |
| Слои | `transport/`, импортирующий Prisma |
| Слои | `application/`, импортирующий Hono |
| Контракты | `packages/contracts`, импортирующий поверхность |

## 5. Контрактные тесты провайдеров

Один набор тестов на порт, прогоняемый против **каждого** драйвера этого порта. Именно это делает утверждение «смена провайдера — изменение конфигурации» проверяемым.

| Порт | Что проверяет набор |
| --- | --- |
| `LlmPort` | Форма запроса и ответа, поведение при таймауте, поведение при отказе, запись `llm_runs` с токенами и стоимостью |
| `KeywordSourcePort` | Разбор CSV, отклонение файла целиком при неверной структуре, соблюдение лимита строк |
| `PublishingPort` | Публикация, снятие с публикации, идемпотентность повторного вызова |
| `ObjectStoragePort` | Presigned upload и download, HEAD, ranged read, delete |

**Отдельный обязательный тест для будущего `MessagingPort`:** dry-run-драйвер не должен открывать сетевое соединение. Тест падает, если попытка была. Этот тест пишется **раньше** самого адаптера — на фазе 2 дорожной карты.

Для E2E используется детерминированный фейковый драйвер `LlmPort`: он возвращает фиксированный текст, не ходит в сеть и делает сценарий воспроизводимым.

## 6. Сквозной E2E-сценарий

Единственный обязательный E2E MVP. Проходит через реальный backend, реальную базу и реальный интерфейс.

```
 1. импорт CSV с ключевыми запросами
 2. создание кластера тем
 3. генерация брифа детерминированным фейковым LLM-драйвером
 4. генерация черновика статьи
 5. попытка публикации БЕЗ одобрения → отказ
 6. одобрение точной ревизии
 7. публикация
 8. проверка метаданных и структурированной разметки статьи
 9. отправка CTA-формы
10. создание лида
11. проверка цепочки атрибуции
```

### Что именно должен доказывать каждый шаг

| Шаг | Утверждение под проверкой |
| --- | --- |
| 1 | Ключи импортированы, нормализованы, дубликаты не созданы |
| 2 | Кластер собран, у него есть опорный ключ, продукт и регион |
| 3 | Бриф сгенерирован через outbox; записан `llm_runs` |
| 4 | Черновик создан как иммутабельная ревизия с `author_kind = llm` |
| **5** | **Публикация без одобрения отклонена. Это ключевой негативный тест всего продукта** |
| 6 | Одобрение записано и привязано к `content_hash` именно этой ревизии |
| 7 | Публикация прошла, `publications.approval_id` заполнен |
| 8 | В **исходном HTML** присутствуют title, description, canonical, теги превью и JSON-LD |
| 9 | Форма отправлена с согласием; без согласия сервер отклоняет |
| 10 | Лид создан со всеми полями, `consent_at` и версиями текстов |
| 11 | Цепочка `лид → касание → статья → кластер → ключ → продукт → регион` восстанавливается целиком |

**Шаг 5 не является формальностью.** Это единственный тест, который доказывает, что главный инвариант продукта работает не только в описании. Дополнительно к нему обязателен тест: правка ревизии после одобрения аннулирует одобрение и вновь делает публикацию невозможной.

### Проверка cookie-изоляции

Отдельный тест, доказывающий два свойства одновременно:

1. cookie авторизации **доходит** до рабочих маршрутов — `/api/service-requests`, `/api/content`, `/api/leads`, `/api/publications`. Регрессия здесь ломает вход в приложение целиком;
2. cookie авторизации **не приходит** на публичный сайт.

Второе свойство на `localhost` не воспроизводится: cookie не различают порты, поэтому установленная `localhost:8080` уходит и на `localhost:5173`. Проверка выполняется против **разных имён хостов** — в staging или в E2E с раздельными хостами, а не на `localhost`. Тест, зелёный только из-за особенности `localhost`, хуже отсутствующего.

Дополнительно проверяется, что ни один изменяющий состояние эндпоинт не отвечает на `GET`, и что `POST`, `PATCH`, `PUT`, `DELETE` отклоняются при чужом `Origin`.

### Проверка границы персональных данных

Отдельно от основного сценария: интеграционный тест, доказывающий, что вызов `LlmPort` не содержит контактных данных. Он остаётся ценным, даже когда правило AC-2 уже стоит в сборке: статический анализ ловит импорт, но не ловит передачу данных, полученных через промежуточный слой.

## 7. Правила для E2E

- Стабильные селекторы и `testID`. Тексты интерфейса меняются чаще, чем поведение.
- Изолированные тестовые данные. Тест не полагается на состояние, оставленное другим тестом.
- Детерминированные утверждения. Ожидание фиксированного времени — источник мигающих падений; ждём условие, а не секунды.
- E2E добавляется, когда предотвращает правдоподобную регрессию и может оставаться стабильным. «Ветка существует» — не повод.
- Внешние вызовы в E2E заменяются фейковыми драйверами.

## 8. Продуктовая валидация

Отдельно от автоматических проверок — то, что доказывает не «код работает», а «продукт работает»:

| Метрика | Что доказывает |
| --- | --- |
| Время от кластера до готового к ревью черновика | Конвейер быстрее ручного письма |
| Доля черновиков, одобренных без переписывания с нуля | Качество приемлемо |
| Стоимость материала из `llm_runs` | Экономика сходится |
| Факт индексации опубликованной статьи | SSG и разметка работают |
| ≥ 1 лид, дошедший до `attribution_touches` с корректной привязкой | **Воронка замкнулась** |
| 0 публикаций без записи одобрения | Комплаенс обеспечен механически, а не на честном слове |

Последняя строка проверяется запросом к базе, а не доверием к процессу.
