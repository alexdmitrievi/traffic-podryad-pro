# Service Requests — центральный контекст

`service_requests` — **входная дверь платформы**. Через неё проходит любая работа: сейчас заявки заводим мы сами, позже это станет клиентским интерфейсом. Это тот контекст, где четыре линии услуг существуют одинаково, но исполняются по-разному.

```
service_request
  └─ service_request_plan (версионируемый)
       └─ approval (привязано к plan hash)
            └─ delivery   ← существует только для seo_content
```

---

## 1. Четыре линии услуг

| `service_line` | Что делает платформа | Предел в MVP |
| --- | --- | --- |
| `seo_content` | Полный цикл: ключи → кластер → бриф → черновик → одобрение → публикация → CTA → лид → атрибуция | `delivered` |
| `b2b_outreach` | Только приём и планирование: ICP, сегменты, ценностные гипотезы, каналы, правовое основание, KPI | `planned_awaiting_capability` |
| `telegram_marketing` | Только приём и планирование: концепция канала, opt-in-механика, контент-план, KPI | `planned_awaiting_capability` |
| `complex_package` | Декомпозиция на дочерние заявки по линиям выше | `partially_delivered` |

### `planned_awaiting_capability` — это не ошибка

Состояние означает: **план готов, одобрен и заархивирован; возможности исполнения в продукте сознательно нет.**

Оно существует ровно для того, чтобы отличить «мы это не умеем по решению» от «заявка застряла и никто не заметил». В интерфейсе оно показывается с явной причиной и ссылкой на фазу из [ROADMAP_OUTREACH_TELEGRAM.md](ROADMAP_OUTREACH_TELEGRAM.md), а не как серый значок «в работе».

Заявка в этом состоянии не считается провалом ни в одном отчёте по воронке. Она считается **выполненной работой по планированию**.

---

## 2. Жизненный цикл

```
draft ──▶ submitted ──▶ triage ──┬──▶ accepted ──▶ planning ──▶ plan_approved ──┬──▶ in_delivery ──▶ delivered
                                 │                                              │
                                 │                                              └──▶ planned_awaiting_capability
                                 └──▶ rejected

Из большинства состояний доступны: on_hold, cancelled
Для complex_package финалом может быть: partially_delivered
```

| Состояние | Смысл | Кто переводит |
| --- | --- | --- |
| `draft` | Заявка создаётся, ещё не подана | Автор |
| `submitted` | Подана, ждёт разбора | Автор |
| `triage` | Разбор: понятна ли задача, наша ли она, какая линия | `admin` |
| `accepted` | Взята в работу | `admin` |
| `rejected` | Не берём. Причина обязательна | `admin` |
| `planning` | Формируется план | `editor` или `admin` |
| `plan_approved` | План одобрен, привязан к hash | `admin` |
| `in_delivery` | Идёт исполнение | система |
| `delivered` | Исполнено полностью | система |
| `planned_awaiting_capability` | Терминальное. План есть, исполнения в продукте нет | система |
| `partially_delivered` | Терминальное для пакета: SEO-часть исполнена, остальные дочерние — в ожидании возможности | система |
| `on_hold` | Пауза по внешней причине. Причина обязательна | `admin` |
| `cancelled` | Отменена. Причина обязательна | `admin` |

**Правила переходов:**

- Каждый переход пишется в `service_request_events`: кто, когда, из чего, во что, по какой причине. Лог append-only.
- Переход в `in_delivery` возможен **только** для `seo_content` и только из `plan_approved`.
- Переход в `plan_approved` возможен только при наличии действующего `approval`, привязанного к текущему hash плана.
- `rejected`, `on_hold` и `cancelled` требуют непустой причины. Отказ без причины — это потерянный контекст для будущей сессии.

## 3. Сущности

### `service_requests`

| Поле | Назначение |
| --- | --- |
| `id`, `workspace_id` | Идентификация |
| `request_number` | Человекочитаемый номер вида `SR-2026-0001` |
| `service_line` | Enum: одна из четырёх линий |
| `vertical` | Ниша. Первая — оптовая дистрибуция нефтепродуктов |
| `title`, `objective` | Что нужно и зачем |
| `target_region_ids[]` | Регионы из справочника |
| `locale` | В MVP всегда `ru` |
| `status` | Состояние из раздела 2 |
| `requested_by` | Автор заявки |
| `parent_request_id` | Для дочерних заявок пакета |
| `origin_lead_id` | Если заявка выросла из входящего лида |
| `deadline_hint` | Необязательный ориентир по срокам |

### `service_request_plans`

Версионируемый артефакт планирования. Новая версия не затирает предыдущую.

| Поле | Назначение |
| --- | --- |
| `request_id`, `version` | Привязка и версия |
| `plan_kind` | Тип плана по линии услуги |
| `content` | Структурированный план (JSON) |
| `content_hash` | Хеш содержимого — то, к чему привязывается одобрение |
| `author_kind` | `human` или `llm` |
| `llm_run_id` | Если план сгенерирован моделью — ссылка на запуск с учётом стоимости |
| `status` | `draft` или `approved` |

### `service_request_events`

Append-only лог переходов. Не редактируется и не удаляется.

## 4. Что содержит план по каждой линии

### `seo_content`

Цели, целевые кластеры и регионы, товарные категории, объём материалов, критерии качества, критерии одобрения, KPI. Этот план **исполним**: за ним следует конвейер из [CONTENT_PIPELINE.md](CONTENT_PIPELINE.md).

### `b2b_outreach`

Портрет идеального клиента, сегменты (отрасль, размер, регион, роль лица принимающего решение), ценностные гипотезы, предполагаемые каналы, **предполагаемое правовое основание коммуникации**, критерии успеха, KPI.

> **План описывает портрет аудитории, а не список людей.** В контексте `planning` нет и не может быть таблицы контактов, поля «получатели» и импорта контактных данных. Это структурное ограничение, а не настройка.

### `telegram_marketing`

Концепция собственного канала, механика opt-in, контент-план, сценарии входящего бота, критерии успеха, KPI.

> **План не содержит списка получателей и механики рассылки.** Только собственный канал и входящие сценарии, где пользователь обращается первым.

### `complex_package`

Декомпозиция на дочерние заявки. Родительская заявка держит общую цель и бюджетную рамку; каждая дочерняя живёт по правилам своей линии. В MVP исполняется только дочерняя заявка `seo_content`; остальные доходят до `planned_awaiting_capability`, и родитель завершается как `partially_delivered`.

## 5. Модель одобрения

**Одобрение — не boolean-поле.** Это отдельная сущность с собственной историей.

### Сущность `approvals`

| Поле | Назначение |
| --- | --- |
| `subject_type` | Что одобряется: ревизия статьи, план, публикация |
| `subject_id` | Идентификатор объекта |
| `content_hash` | **Хеш точного содержимого**, которое одобрили |
| `decision` | `approved` или `rejected` |
| `decided_by` | Пользователь-одобряющий |
| `decided_at` | Отметка времени |
| `note` | Комментарий. Обязателен при отказе |

### Пять инвариантов

1. **Одобрение привязано к точному содержимому.** `content_hash` фиксирует именно ту версию, которую видел человек.

2. **Изменение содержимого аннулирует одобрение автоматически.** Новый текст — новый hash — прежнее одобрение больше не соответствует объекту. Это не проверка «не забыть переодобрить»: несоответствие hash делает публикацию невозможной.

3. **Публикация без одобрения невозможна на уровне схемы.** `publications.approval_id NOT NULL` с внешним ключом. Это не проверка в коде, которую можно обойти новым роутом или скриптом.

4. **Автор и одобряющий записываются раздельно** — даже когда это один и тот же человек. В MVP пользователь одобряет всё сам, и это нормально. Но данные для включения политики «одобряющий ≠ автор» собираются с первого дня: иначе при переходе на двух ревьюеров придётся переразмечать всю историю.

5. **Всё аудируется.** Каждое решение попадает в `audit_log` вместе с ролью, временем и объектом.

### Единственный одобряющий: осознанные следствия

| Следствие | Решение |
| --- | --- |
| Автор и одобряющий совпадают | Принято для MVP. Разделение включается политикой, не миграцией |
| Одобряющий недоступен — конвейер стоит | **Так и задумано.** Ничего не публикуется «по таймауту» и не одобряется автоматически |
| Bus factor равен единице | Признанный риск MVP. Резервный одобряющий добавляется назначением роли `admin`, без изменения кода |

## 6. Что происходит с заявкой B2B и Telegram: пример

```
1. draft            Заводим заявку "Выход на автопарки Тюменской области"
2. submitted        Подаём
3. triage           Разбор: линия b2b_outreach
4. accepted         Берём в работу
5. planning         Готовим план: ICP, сегменты, гипотезы, каналы, правовое основание, KPI
6. plan_approved    Пользователь одобряет план; approval привязан к plan hash
7. planned_awaiting_capability
                    Терминальное состояние.
                    В интерфейсе: "План одобрен. Исполнение недоступно:
                    возможности исходящей коммуникации нет в продукте.
                    См. фазу 1 дорожной карты."
```

Заявка **закрыта успешно**. Продукт сделал ровно то, что умеет, и явно сказал, чего не умеет и почему.
