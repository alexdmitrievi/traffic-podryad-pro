# Атрибуция

Атрибуция — то, ради чего существует весь остальной конвейер. Без неё контент-производство остаётся актом веры: материалы выходят, лиды приходят, но связи между ними никто не видит.

**Цель MVP:** для каждого лида ответить на вопрос — по какому запросу, из какого кластера, о каком продукте и в каком регионе он пришёл, и какая статья его привела.

---

## 1. Цепочка

```
lead
 └─ attribution_touch (first / last)
     └─ content_item (статья)
         └─ topic_cluster
             ├─ keyword (опорный + связанные)
             ├─ product
             └─ region
```

Каждое звено — реальный внешний ключ, а не восстановление по совпадению строк постфактум.

---

## 2. Идентификация посетителя

Публичный сайт статичен, поэтому идентификатор визита ставит и читает скрипт сайта.

| Свойство | Значение |
| --- | --- |
| Имя cookie | `ATTRIBUTION_COOKIE_NAME`, по умолчанию `pip_vid` |
| Содержимое | Случайный идентификатор. **Никаких персональных данных** |
| Хост | `pipupi.ru`, host-only |
| Срок жизни | `ATTRIBUTION_COOKIE_TTL_DAYS`, по умолчанию 90 дней |
| `Secure` | `true` |
| `SameSite` | `Lax` |
| `HttpOnly` | `false` — иначе скрипт не сможет её прочитать |

`visitor_id` — **не учётная запись и не даёт никаких прав**. Это случайное число, которое связывает несколько просмотров в одну сессию посетителя.

Никаких сторонних пикселей, счётчиков и трекеров на публичном сайте в MVP нет. Все события идут в собственный API и собственную базу.

---

## 3. Касания

`attribution_touches` — записи о взаимодействии посетителя с контентом.

| Поле | Назначение |
| --- | --- |
| `visitor_id` | Идентификатор из cookie |
| `lead_id` | Заполняется задним числом, когда посетитель становится лидом |
| `content_item_id` | Статья, если посетитель был на её странице |
| `path` | Путь страницы |
| `referrer` | Источник перехода |
| `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term` | Метки, если есть |
| `occurred_at` | Время |
| `position` | `first` или `last` — вычисляется при связывании с лидом |

Касания пишутся до того, как человек оставил заявку. В момент отправки формы накопленная история визитов **связывается с лидом** по `visitor_id`.

---

## 4. Модель атрибуции

`ATTRIBUTION_MODEL=first_last` — храним оба края:

- **first touch** — первая статья, приведшая посетителя на сайт. Отвечает на вопрос «что работает на привлечение».
- **last touch** — последняя статья перед заявкой. Отвечает на вопрос «что работает на конверсию».

Это две разные метрики, и подменять одну другой — типичная ошибка при оценке контента. Информационная статья часто выигрывает по first touch и проигрывает по last touch; коммерческая — наоборот. Обе нужны.

Мультитач-модели с распределением веса между касаниями в MVP не реализуются: они требуют больше данных, чем у нас будет, и дают точность, которую не на чем проверить.

**Ограничение, которое надо принять сразу.** Атрибуция по cookie не видит: переходы между устройствами, посетителей, очистивших cookie, и приход по каналам без реферера. Это известная граница метода, а не дефект реализации. Цифры атрибуции — нижняя оценка, а не полная картина.

## 5. Форма лида

Форма запроса цены — единственная точка входа лида в MVP.

### Поля

| Поле | Обязательное | Комментарий |
| --- | --- | --- |
| Товарная категория / продукт | да | Из справочника, см. [PETROLEUM_TAXONOMY.md](PETROLEUM_TAXONOMY.md) |
| Объём | да | Число + единица измерения |
| Регион поставки | да | Из справочника регионов |
| Базис поставки | нет | Из справочника вариантов |
| Название компании | нет | — |
| ИНН | нет | Персональные / идентифицирующие данные |
| Контактное лицо | да | Персональные данные |
| Телефон | одно из | Персональные данные |
| Email | одно из | Персональные данные |
| Комментарий | нет | Свободный текст |
| **Согласие на обработку** | **да** | Непредотмеченный чекбокс |

### Скрытые поля, заполняемые сайтом

`visitor_id`, `landing_path`, `utm_*`, `content_item_id` страницы, с которой отправлена форма.

### Обязательные проверки на сервере

- Согласие отсутствует → **запрос отклоняется**. Это серверная проверка, а не скрытая кнопка в интерфейсе.
- Фиксируются `consent_at`, `consent_text_version`, `privacy_policy_version` — известно, на какую именно редакцию текста человек согласился.
- Rate limit по IP и по отпечатку запроса.
- Honeypot-поле: заполнено — тихо отклоняем.
- Серверная валидация всех полей по схеме из `packages/contracts`.

Обхода капчи в продукте нет и не будет — см. [COMPLIANCE.md](COMPLIANCE.md).

### Дедупликация

`dedupe_hash` из нормализованных контактных данных и продукта. Повторная заявка того же человека по тому же продукту в коротком окне не создаёт второй лид, но **добавляет касание** — повторное обращение само по себе сигнал.

## 6. Персональные данные

| Правило | Реализация |
| --- | --- |
| Данные лидов не покидают российский регион | Managed PostgreSQL в российском регионе |
| Данные лидов и атрибуции не уходят к LLM | Правило AC-2 + `PII_TO_LLM_ALLOWED=false` |
| `visitor_id` не содержит персональных данных | Случайное значение |
| Согласие версионируется | `consent_text_version`, `privacy_policy_version` |
| Ретенция | Периодическая задача удаления по истечении срока |
| Права субъекта | Выгрузка и удаление по запросу, с записью в `audit_log` |

Модель никогда не получает содержимое `leads` и `attribution_touches` — включая поле «комментарий», куда человек может написать что угодно, в том числе персональные данные третьих лиц.

## 7. Экран воронки

Минимальный набор, который делает MVP осмысленным:

| Метрика | Ответ на вопрос |
| --- | --- |
| Опубликованных материалов | Сколько произвели |
| Просмотров по материалам | Что читают |
| Лидов всего | Сколько получили |
| Конверсия просмотр → лид по материалу | Что работает |
| Лиды по кластерам | Какие темы приносят спрос |
| Лиды по продуктам | Какая номенклатура востребована |
| Лиды по регионам | Где спрос |
| First touch vs last touch | Что привлекает vs что конвертирует |
| Стоимость материала из `llm_runs` | Сходится ли экономика |

Демонстрационных данных и «красивых» графиков на пустой базе не показываем: пустой экран честнее выдуманного.

---

## 8. Критерий готовности

MVP по атрибуции считается работающим, когда на проде выполняется цепочка:

```
существует лид
  → у него есть связанное касание
    → касание указывает на конкретную статью
      → статья принадлежит кластеру
        → у кластера есть опорный ключ, продукт и регион
```

и вся цепочка проверяется автоматически — шаг 11 сценария E2E из [TESTING.md](TESTING.md).
