# Локальная база данных

Локальный PostgreSQL поднимается **Docker Compose**, а не нативной установкой. Требование одинаково для Windows, macOS и Linux: разработчику не нужны ни установленный PostgreSQL, ни облачные доступы.

> **Файла `docker-compose.yml` в репозитории пока нет** — он появится в Wave 2. Этот документ фиксирует, каким он должен быть.

---

## 1. Целевая конфигурация

| Параметр | Значение | Почему |
| --- | --- | --- |
| Образ | `postgres:18-alpine` | Мажорная версия 18 даёт нативную `uuidv7()`. Локально мы её используем независимо от того, чем закончится вопрос продакшн-версии |
| Расширения | **нет** | См. раздел 2.1: базовый образ не содержит `pgvector`, и включать его пока незачем |
| База разработки | `pipupi` | — |
| Порт разработки | `54329` | Нестандартный: не конфликтует с уже установленным локально PostgreSQL на `5432` |
| Тестовая база | `pipupi_test` | Отдельный сервис из того же образа |
| Порт тестов | `POSTGRES_TEST_PORT` | Настраиваемый: параллельные прогоны не мешают друг другу |
| Том данных | Именованный том | Данные переживают пересоздание контейнера |

## 2. Расхождение с продакшном

Локально `postgres:18-alpine`.

> ⚠️ **Локальная конфигурация ничего не доказывает о продакшне.** Управляемый сервис — это другая СУБД под тем же именем: своя мажорная версия, свой закрытый список разрешённых расширений, свои ограничения на типы индексов. Из того, что `uuidv7()` работает в контейнере, **не следует**, что оно работает в Yandex Managed Service for PostgreSQL. Пока не пройден verification gate из раздела 3 [DEPLOYMENT.md](DEPLOYMENT.md), возможности продакшн-базы считаются неизвестными.

### 2.1. Почему `pgvector` не включён локально

Официальный образ `postgres:18-alpine` **не содержит** расширение `vector`. Чтобы получить его локально, нужен другой образ — например, из проекта `pgvector`, — а это отдельный тег, который тоже требует проверки.

Мы этого не делаем сейчас по трём причинам:

1. **Ничему в репозитории он пока не нужен.** Нет схемы, нет колонок эмбеддингов, нет векторных индексов.
2. **Продакшн-ворота не пройдены.** Неизвестно, поддерживает ли `pgvector` управляемый сервис и какой тип индекса там доступен. Включить расширение локально раньше — значит начать писать код против возможности, которой может не оказаться в продакшне.
3. **Локальный образ под векторы выбирается в Wave 3** — вместе с появлением первой колонки эмбеддингов и только после того, как ворота ответят, нужны ли векторы в базе вообще.

`scripts/repo-env.mjs` следит за обоими краями: он падает, если в схеме появляется векторная колонка или индекс, и падает, если `docker-compose.yml` переключается на образ с `pgvector`, пока ворота открыты.

Расхождение управляемо **при одном условии**: схема не должна опираться на возможности, наличие которых в продакшне не подтверждено. Практически это означает два решения.

**UUIDv7:**

- если продакшн даёт PostgreSQL 18 — генерация ID остаётся в базе;
- если нет — UUIDv7 генерирует приложение, тип колонки остаётся нативный `uuid`, локальная разработка не меняется.

**Второй вариант работает на обеих версиях**, поэтому до подтверждения продакшн-версии схема пишется под него. Это осознанный выбор в пользу переносимости, а не недосмотр.

**Векторы:** колонки эмбеддингов и векторные индексы **не попадают в миграции** до закрытия ворот — иначе первая же попытка применить миграцию на продакшне упрётся в недоступное расширение, причём после того, как остальная схема уже поедет. См. раздел 2.1.

Интеграционные тесты гоняются против того же образа, что и разработка. Это не гарантирует полного совпадения с продакшном, но ловит основную массу расхождений между кодом и реальной базой — в отличие от моков, которые не ловят ничего.

## 3. Порядок работы

Доступно с Wave 2:

```bash
# 1. Проверить, что Docker установлен и демон запущен
docker compose version
docker info

# 2. Подготовить переменные окружения
cp backend/.env.example backend/.env

# 3. Поднять базу разработки
bun run db:start        # docker compose up -d postgres

# 4. Посмотреть состояние
bun run db:status

# 5. Остановить
bun run db:stop
```

Тестовая база — отдельный сервис `postgres_test` на порту `POSTGRES_TEST_PORT` (по умолчанию `54330`): `bun run db:start:test`. Интеграционный раннер будет поднимать и подготавливать её сам, когда появится в Wave 3.

Появится в Wave 3, вместе со схемой:

```bash
bun run --cwd backend prisma:migrate   # применить миграции
bun run --cwd backend prisma:seed      # справочники: регионы, товарные категории
```

## 4. Сид-данные

Сиды заполняют **только справочники**, без которых система бессмысленна:

| Что | Источник |
| --- | --- |
| Регионы: СФО, УФО и города | [PETROLEUM_TAXONOMY.md](PETROLEUM_TAXONOMY.md) |
| Товарные категории | Там же |
| Единицы измерения | Там же |
| Учётная запись администратора для разработки | Только в среде разработки |

Чего сиды **не** делают: не создают демонстрационных статей, лидов, фейковой аналитики и «красивых» графиков. Пустой экран честнее выдуманных данных, а демо-данные имеют свойство доезжать до продакшна.

Сид товарных позиций **не содержит технических характеристик, нормативов и цен** — только наименования, категории, единицы и синонимы для разметки ключевых запросов.

---

## 5. Согласованность конфигурации

Имена баз, порты, учётные данные, теги образов и пути томов должны совпадать в трёх местах:

- `docker-compose.yml`;
- `backend/.env.example`;
- этот документ.

Расхождение между ними — это полдня чужого времени на ровном месте. При изменении любого из значений обновляются все три.

---

## 6. Секреты

Учётные данные локальной базы — не секрет и живут в `.env.example` открыто: они не дают доступа никуда, кроме контейнера на машине разработчика.

Всё остальное — ключ DeepSeek, доступы к объектному хранилищу, ключ подписи JWT — **в `.env.example` присутствует только плейсхолдером**. Реальные значения живут в `.env`, который не попадает в Git.
