# Wave 4 — рабочее задание и протокол ревью

Wave 4 реализует первый вертикальный срез. Исполнитель — DeepSeek V4 Pro; архитектурный и ревью-слой — Claude. Этот документ описывает, что должно быть сделано, по каким критериям это принимается и что проверяется на ревью.

---

## 1. Роли

| Кто | Что делает |
| --- | --- |
| **Исполнитель** | Пишет код юнита, доводит `bun run check` и `bun run test` до зелёного, открывает PR |
| **Ревьюер** | Проверяет смысл: инварианты, границы, краевые случаи. Не проверяет то, что уже проверяет CI |
| **Владелец продукта** | Одобряет переход между волнами и решения, помеченные как «обратимые» |

Разделение работает только при одном условии: **исполнитель прогоняет проверки до передачи.** Иначе ревью тратится на механические нарушения границ, которые CI и так поймает.

---

## 2. Контракт передачи

```bash
bun run check   # AC-1, AC-2, AC-3, границы слоёв, repo-env, секреты, CLAUDE.md = AGENTS.md
bun run test    # контракты, схема, сиды, фикстуры самих проверок
bun run typecheck
```

Зелёные — необходимое условие приёмки, но не достаточное. Достаточность даёт раздел 5.

Правила, которые проверка обеспечивает механически, в ревью не обсуждаются: они либо прошли, либо PR не готов. Обсуждается то, чего проверка не видит.

---

## 3. Декомпозиция

Шесть юнитов, строгий порядок, отдельный PR на каждый. Юнит целиком влезает в одно ревью; Wave 4 одним куском — нет.

| Юнит | Содержимое |
| --- | --- |
| **4a** Рантайм | `prisma.config.ts`, первая миграция, `env.ts`, `db.ts`, `runtime.ts`, `app.ts`, health, `outbox/`, `background-tasks.ts`, `jobs.ts` + `cron`/`scheduler`/`worker` |
| **4b** Авторизация | `modules/auth`, `modules/users`, host-only cookie, две политики CORS, проверка `Origin` |
| **4c** Порты | `providers/llm` (фейк + DeepSeek), `providers/keywords` (CSV), `providers/publishing`, общий контрактный сьют |
| **4d** Модули | service-requests, planning, research, content, approvals, publishing, leads, attribution, analytics |
| **4e** Поверхности | `website` (Astro SSG), `webapp` (React CSR) |
| **4f** E2E | Сквозной сценарий из 11 шагов ([TESTING.md](TESTING.md) §6) |

Каждый следующий опирается на предыдущий. Пропуск порядка означает, что юнит нечем протестировать.

## 4. Критерии приёмки по юнитам

### 4a — Рантайм

**Схема:** добавляется `TaskOutbox` + enum `TaskOutboxStatus`. Первая миграция генерируется из схемы; SQL руками не пишется.

**Обязательно доказано тестами:**

- Процесс **отказывается стартовать** при `REQUIRE_HUMAN_APPROVAL=false`, `OUTBOUND_MESSAGING_ENABLED=true`, `PII_TO_LLM_ALLOWED=true` и при `AUTH_COOKIE_SECURE=false` в продакшне. Отказ — ненулевой код выхода, а не запись в лог.
- `/health/live` **не обращается к базе.** Иначе кратковременная недоступность базы вызывает перезапуск, который её не чинит.
- `/health/ready` отвечает отрицательно, пока миграции не применены.
- Outbox: захват строки с fencing-токеном, повтор с задержкой, ключ дедупликации, возврат просроченной аренды без потери счётчика попыток. Интеграционные тесты против Docker PostgreSQL.
- Два процесса, одновременно дренирующие outbox, не выполняют одну задачу дважды.
- `jobs.ts` содержит **только type-импорты** — реестр читается инструментами без базы и до `prisma generate`.
- Graceful shutdown укладывается в общий дедлайн и дренирует принятые задачи.

**Автоматически:** `repo-env` перестанет пропускать placeholder-`typecheck` у backend, как только там появятся `.ts`. Это ожидаемо — `typecheck` должен стать настоящим в этом же PR.

### 4b — Авторизация

- Ротация refresh-токена атомарна; повтор старого вне окна гонки **отзывает сессию**.
- Роль резолвится из активной сессии на каждом запросе, а не из токена. Тест: понижение роли действует немедленно.
- Состояние «ноль администраторов» невозможно; самопонижение последнего администратора отклоняется.
- Cookie: `Domain` не задан, `Path=/`, `HttpOnly`, `Secure` в продакшне, `SameSite=Lax`.
- Изменяющие состояние эндпоинты **не отвечают на `GET`**; `Origin` проверяется для `POST`, `PATCH`, `PUT`, `DELETE` независимо от CORS.
- Две политики CORS: публичная без учётных данных, приложенческая с ними.
- Тест изоляции cookie гоняется против **разных имён хостов**, не `localhost` — там cookie не различают порты и тест был бы зелёным по ложной причине.

### 4c — Порты

- Один контрактный сьют на порт прогоняется против **всех** драйверов порта.
- `LlmPort`: рантайм-guard отклоняет payload с персональными данными. Тест передаёт объект с телефоном и email и ожидает отказ. AC-2 ловит импорт; этот тест ловит передачу.
- Каждый вызов пишет `LlmRun`: провайдер, модель, назначение, хеш промпта, токены, стоимость, задержка, статус. В логи не попадают ни промпт, ни ответ.
- Превышение `LLM_MONTHLY_COST_CAP_RUB` останавливает генерацию, а не продолжает молча.
- `KeywordSourcePort`: файл принимается или отклоняется **целиком**. Частичный импорт запрещён.
- `PublishingPort`: повторная публикация идемпотентна.

### 4d — Модули

- Публикация без действующего одобрения возвращает отказ. **Это ключевой негативный тест продукта.**
- Правка ревизии после одобрения аннулирует его; следующая попытка публикации снова отклоняется.
- `b2b_outreach` и `telegram_marketing` доходят до `planned_awaiting_capability` и **не имеют** пути в `in_delivery`.
- `complex_package` декомпозируется; исполняется только дочерняя SEO-заявка, родитель завершается как `partially_delivered`.
- Каждый переход статуса пишется в `service_request_events`; `rejected`, `on_hold`, `cancelled` требуют причины.
- Лид без согласия отклоняется **сервером**.
- Дедупликация лида добавляет касание, а не второй лид.

### 4e — Поверхности

- SEO-критичное содержимое — title, description, canonical, теги превью, JSON-LD — присутствует в **исходном HTML**, а не появляется скриптом.
- `canonical` всегда указывает на форму без `www`.
- Публичный сайт не получает cookie авторизации.
- Пустые состояния показываются как пустые. Демонстрационных данных и графиков на пустой базе нет.
- Lighthouse-бюджет для страницы статьи соблюдён.

### 4f — E2E

Сценарий из [TESTING.md](TESTING.md) §6, все 11 шагов. Шаг 5 — попытка публикации без одобрения — обязателен и не заменяется юнит-тестом.

## 5. Что проверяет ревью

CI проверяет границы. Ревью проверяет то, что выглядит правильно и работает неправильно.

**Инварианты — реализованы, а не описаны**

- [ ] Гварды окружения действительно **останавливают процесс**, а не пишут `warn`
- [ ] Сравнение `content_hash` выполняется на сервере перед публикацией, а не только в UI
- [ ] `publications.approval_id` заполняется реальным одобрением, а не любым найденным
- [ ] Одобрение с чужим или устаревшим хешем отклоняется

**Границы — по смыслу, а не по формальному признаку**

- [ ] `application` не получил Prisma через промежуточный реэкспорт
- [ ] `providers/llm` не получил данные лида через объект, собранный слоем выше
- [ ] Порт объявляет операции продукта, а не проксирует SDK один в один
- [ ] Репозиторий выражает продуктовые операции, а не generic CRUD

**Краевые случаи**

- [ ] Что происходит при падении LLM на середине генерации: задача остаётся в outbox или теряется
- [ ] Что происходит при двух одновременных одобрениях одной ревизии
- [ ] Что происходит при повторной отправке формы лида с тем же телефоном
- [ ] Что происходит при истечении аренды outbox во время выполнения

**Гигиена**

- [ ] Новые переменные окружения добавлены в `backend/.env.example`, в `docs/` и, если они критичны для комплаенса, в `scripts/repo-env.mjs`
- [ ] `CLAUDE.md` и `AGENTS.md` изменены синхронно или не изменены вовсе
- [ ] Миграция совместима вперёд: откат кода не требует отката схемы
- [ ] Ни одного секрета, ни одного реального значения в примерах

## 6. Решения, принятые по умолчанию

Приняты, чтобы не блокировать работу. Каждое обратимо — скажите, и поменяю.

| Решение | Значение | Почему |
| --- | --- | --- |
| **Кластеризация** | Косинусное сходство **в памяти приложения**; в базе только состав кластера | Снимает зависимость от непройденных ворот `pgvector` целиком. На тысячах ключей считается мгновенно. Переход на расширение потом — добавление колонки и индекса, а не переделка |
| **LLM в 4c** | Только детерминированный фейковый драйвер; боевой DeepSeek — отдельным шагом после ревью границы ПДн и учёта стоимости | Нулевой риск случайных трат и утечек, пока конвейер собирается |
| **Боевой DeepSeek (после Wave 4)** | Ревью границы ПДн пройдено: payload'ы порта не несут ПДн, рантайм-guard отклоняет телефон/email/ИНН, AC-2 в CI. Учёт стоимости реализован: цены + курс + лимит обязательны при заданном ключе, счёт пишется в `llm_runs` в рублях. Включение — `LLM_PROVIDER=deepseek` + ключ в `.env`; живая проверка — `bun run --cwd backend test:live` | Траты возможны только с заданным лимитом и после живой проверки контракта |
| **Передача работы** | Отдельная ветка на юнит, PR в feature-ветку | CI гоняет проверки сам, ревью привязано к строкам |
| **Источник эмбеддингов** | **Не выбран** | Наличие endpoint'а эмбеддингов у DeepSeek я не проверял. Проверить до старта 4c; при отсутствии — лексическая кластеризация на первый срез |

## 7. Запрещено в любом юните

Не обсуждается, не «временно», не «для теста»:

- отправка исходящих сообщений в любом канале;
- хранение контактов третьих лиц для рассылки;
- MTProto, автоматизация аккаунтов, приглашения, сбор участников;
- обход капчи и банов;
- передача персональных данных LLM-провайдеру;
- публикация без записи одобрения;
- `AUTH_COOKIE_DOMAIN` в любом виде;
- векторные колонки и индексы до прохождения ворот из [DEPLOYMENT.md](DEPLOYMENT.md) §3;
- секреты в коде, документации, примерах и истории Git;
- n8n и любой внешний оркестратор;
- новая инфраструктура без записанного измерения ([ARCHITECTURE.md](ARCHITECTURE.md) §6).

Первые пять обеспечены правилами AC-1…AC-3 и `repo-env`. Остальные — предмет ревью.

## 8. Порядок работы над юнитом

1. Исполнитель читает [ARCHITECTURE.md](ARCHITECTURE.md), [COMPLIANCE.md](COMPLIANCE.md) и документ, относящийся к юниту.
2. Пишет код и тесты в отдельной ветке.
3. Доводит `bun run check`, `bun run test`, `bun run typecheck` до зелёного.
4. Открывает PR с описанием: что сделано, какие краевые случаи покрыты, какие решения приняты и почему.
5. Ревьюер проходит раздел 5 и оставляет замечания построчно.
6. После исправлений — влитие и переход к следующему юниту.

Юнит не считается готовым, пока его критерии приёмки из раздела 4 не выполнены целиком. Частично готовый юнит не открывает следующий.
