# Разделение браузерных поверхностей

Две браузерные поверхности, разделённые по одному признаку — **нужен ли странице SEO**. Отнесение функции не к той поверхности — самая частая ранняя ошибка, и исправлять её потом дороже, чем решить сейчас.

| Поверхность | Адрес | Технология | Кто читает |
| --- | --- | --- | --- |
| `website` | `pipupi.ru` | Astro, SSG | Поисковые системы и анонимные посетители |
| `webapp` | `app.pipupi.ru` | React, CSR | Авторизованные сотрудники |

---

## Правило

> **Если страница должна ранжироваться в поиске или корректно превьюиться при отправке ссылкой — она в `website`. Если страница доступна только после входа — она в `webapp`.**

Не переносим SEO-страницы в `webapp` ради «единого приложения»: это теряет ровно то, ради чего продукт существует. Не тащим приложение в Astro ради «единого рендерера»: за авторизацией никакому краулеру ничего не нужно, и CSR там проще и дешевле.

---

## Что где живёт

### `website` — `pipupi.ru`

| Раздел | Содержимое |
| --- | --- |
| Главная | Позиционирование продукта |
| Страницы услуг | Четыре линии: `seo_content`, `b2b_outreach`, `telegram_marketing`, `complex_package` |
| Статьи | Опубликованные материалы — основной SEO-актив |
| Страницы кластеров | Тематические хабы со ссылками на материалы |
| Региональные страницы | Разрезы по СФО и УФО |
| Продуктовые страницы | Категории нефтепродуктов |
| CTA-формы | Запрос цены |
| Правовые страницы | Политика конфиденциальности, текст согласия на обработку |
| Служебное | `sitemap.xml`, `robots.txt`, JSON-LD |

### `webapp` — `app.pipupi.ru`

| Раздел | Содержимое |
| --- | --- |
| `/app/service-requests` | Заявки: создание, разбор, статусы |
| `/app/planning` | Версионируемые планы по всем линиям |
| `/app/research` | Ключевые запросы, метрики, кластеры |
| `/app/content` | Брифы, редактор, ревизии |
| `/app/approvals` | Очередь одобрения |
| `/app/publications` | Публикации и их статусы |
| `/app/leads` | Лиды |
| `/app/funnel` | Воронка и атрибуция |
| `/admin/*` | Пользователи, роли, справочники, аудит |

Админка — **дерево роутов внутри `webapp`**, а не отдельное приложение. Отдельный деплой ради ролевого разграничения — лишний артефакт без выигрыша.

## Разбор спорных случаев

| Случай | Куда | Почему |
| --- | --- | --- |
| Предпросмотр статьи до публикации | `webapp` | Виден только редактору; индексироваться не должен |
| Опубликованная статья | `website` | Ради индексации она и создавалась |
| Форма запроса цены | `website` | Должна быть на публичной странице рядом с контентом |
| Просмотр пришедших лидов | `webapp` | За авторизацией |
| Страница услуги «B2B outreach» | `website` | Публичное предложение, должно находиться поиском |
| Заведение заявки на эту услугу | `webapp` в MVP | Заявки заводим внутри. Публичный интейк — когда пойдём в клиентский режим |
| Публичный статус заявки по ссылке-токену | `website` | Если понадобится — с `noindex` |

## Правила `website`

1. **SEO-критичное содержимое присутствует в исходном HTML.** Title, description, canonical, теги превью, заголовки, тексты. Скрипты могут дополнять страницу, но не могут быть единственным источником такого содержимого.
2. **Чистый SSG.** Ни ISR, ни SSR в MVP. Публикация — событие в outbox: сборка → выгрузка в объектное хранилище → инвалидация CDN.
3. **Минимум JavaScript.** Интерактивность — только там, где она действительно нужна: формы и переключатели. Скорость страницы — часть продукта, а не украшение.
4. **Никаких сторонних счётчиков и пикселей** в MVP. Аналитика собственная.
5. **`canonical` — всегда форма без `www`.** См. [DOMAINS.md](DOMAINS.md).
6. **Публичный сайт не владеет авторизацией.** Cookie авторизации host-only на `api.pipupi.ru` и на публичный сайт не приходит — это часть модели безопасности, а не деталь конфигурации.

---

## Правила `webapp`

1. Серверным состоянием владеет слой server-state, состоянием форм — слой форм. Не изобретаем третий подход.
2. Схемы приходят только из `packages/contracts`. Формы API не переписываются руками.
3. `src/components/ui` и платформенный слой **никогда** не импортируют продуктовые фичи. Фичи могут использовать платформу и UI-примитивы; кросс-фича — только через публичный индекс целевой фичи.
4. Роуты и точка входа — тонкие композиционные файлы.
5. Два непересекающихся дерева за авторизацией: `/app/*` и `/admin/*`, с ролевыми guard'ами.
6. Refresh-credential **никогда** не попадает в `localStorage`, `sessionStorage` или другое JS-читаемое хранилище.
7. Демонстрационные данные и графики на пустой базе не показываем. Пустое состояние честнее выдуманного.

---

## Общее

- Обе поверхности используют одни и те же Zod-схемы из `packages/contracts`.
- Обе обращаются к одному API на `api.pipupi.ru`, но по разным политикам CORS: публичные эндпоинты без учётных данных, приложение — с ними.
- Дублирования логики между поверхностями быть не должно: если правило нужно обеим — его место в контрактах или в backend, а не в двух копиях.

---

## Будущая мобильная поверхность

Отложена. Когда появится — использует `api.pipupi.ru`, своего хоста не получает и работает по отдельному набору маршрутов, обменивающих токены в теле запроса вместо cookie. Правила разделения `website` и `webapp` на неё не распространяются: это третья поверхность со своими ограничениями, а не вариант одной из существующих.
