# Архитектура

Pipupi — **модульный монолит**: один backend-кодовый базис, одна база данных, общие контракты и явные границы контекстов внутри репозитория. Backend может выставлять несколько точек входа (API, worker, cron), но они разделяют схему Prisma, валидацию окружения, сервисы и контракты.

Подход — **прогрессивный DDD-lite**. У каждого продуктового контекста есть владелец и направление зависимостей, но не у каждого обязаны быть все слои. `domain/` появляется тогда, когда у контекста есть настоящие правила, расчёты или переходы состояний. Пустые слои, generic-репозитории, CQRS и event sourcing как декорация — не добавляем.

---

## 1. Форма системы

```
                       pipupi.ru (Astro SSG)          app.pipupi.ru (React CSR)
                              │                                │
                              │  публичные эндпоинты           │  эндпоинты за авторизацией
                              └────────────┬───────────────────┘
                                           ▼
                                   api.pipupi.ru (Hono)
                                           │
        ┌──────────────────────────────────┼──────────────────────────────────┐
        ▼                                  ▼                                  ▼
   modules/*                         providers/*                     outbox · jobs · tasks
   продуктовые контексты          порты к внешнему миру              фоновая работа
        │                                  │                                  │
        └──────────────────────────────────┴──────────────────────────────────┘
                                           ▼
                                     PostgreSQL
```

Одна база. Один процесс API. Фоновая работа — в той же кодовой базе, запускается отдельными точками входа из того же образа.

---

## 2. Контракты

`packages/contracts` — единственный источник правды для payload'ов API, DTO и формы ошибок. Новый эндпоинт начинается со схемы Zod здесь.

- Backend валидирует ими входящие запросы и генерирует из них OpenAPI.
- `webapp` использует их же в формах и API-клиентах.
- `website` подключает их, когда начинает читать данные API.

Формы API не переписываются руками в клиентах. Изменение контракта проверяется у производителя и всех потребителей за один проход.

Конверт ошибки — стабильный и общий для всего API:

```
{ "error": { "code": "...", "message": "...", "details": ... } }
```

`code` — закрытый enum в контрактах. Транспорт переводит доменные отказы в этот конверт; бизнес-правила в обработчиках Hono не живут.

## 3. Backend: модули

```
backend/src/modules/<context>/
  index.ts          единственная точка кросс-контекстного импорта
  transport/        Hono, HTTP-валидация и представление
  application/      сценарии, права, транзакции, оркестрация, порты
  domain/           опционально: чистые правила, переходы, расчёты
  infrastructure/   Prisma и адаптеры провайдеров
```

Направление зависимостей: `transport → application → domain / ports → infrastructure → DTO`.

**Инварианты:**

- `transport/` не импортирует Prisma.
- `application/` и `domain/` не импортируют Hono, Prisma, конфигурацию окружения и SDK провайдеров.
- `infrastructure/` реализует порты своего контекста. Репозитории выражают продуктовые операции, а не generic-CRUD.
- Кросс-контекстное взаимодействие — только через публичный `index.ts` или явный порт приложения. Никогда во внутренности чужого контекста.

Правило длины файла архитектурным не является. Архитектура здесь — про владение и направление зависимостей.

### Состав модулей MVP

| Модуль | Владеет |
| --- | --- |
| `auth` | Учётные записи, сессии, токены, сброс пароля |
| `users` | Профили, роли, административные операции над пользователями |
| `service-requests` | Заявки на услуги, жизненный цикл, декомпозиция пакетов |
| `planning` | Версионируемые планы по всем четырём линиям. **Только планы, никакой отправки** |
| `research` | Ключевые запросы, метрики, кластеризация тем |
| `content` | Брифы, статьи, иммутабельные ревизии |
| `approvals` | Шлюз одобрения. Единственный способ разрешить публикацию |
| `publishing` | Публикации, целевые площадки, публичные URL |
| `leads` | Захват лидов, дедупликация, согласия |
| `attribution` | Визиты, касания, связь лида с контентом |
| `analytics` | Срезы воронки поверх собственных данных |

## 4. Providers: порты и адаптеры

Всё внешнее живёт в `backend/src/providers/**`. Это сервисы уровня backend, а не продуктовые модули.

```
backend/src/providers/<capability>/
  port.ts               интерфейс в терминах продукта
  <driver>.ts           реализация для конкретного провайдера
  contract-suite.ts     один набор тестов, прогоняемый против всех драйверов
```

| Порт | Операции | Драйвер в MVP |
| --- | --- | --- |
| `LlmPort` | `generateBrief`, `generateDraft` | DeepSeek (`DEEPSEEK_BASE_URL`, `DEEPSEEK_MODEL`) |
| `KeywordSourcePort` | `importKeywords` | CSV |
| `PublishingPort` | `publish`, `unpublish` | Внутренний сайт на Astro |
| `ObjectStoragePort` | presigned upload / download, HEAD, ranged read, delete | S3-совместимый |
| `MessagingPort` | — | **отсутствует** |

Смена провайдера должна быть изменением конфигурации, а не кода. Один контрактный набор тестов против всех драйверов порта — то, что делает это утверждение проверяемым, а не декларативным.

**`MessagingPort` в MVP отсутствует физически.** Это не выключенный флаг и не заглушка: адаптера отправки в репозитории нет, а правило AC-3 не даёт добавить соответствующую зависимость.

## 5. Фоновая работа

Три механизма, разделённые одним вопросом: **что произойдёт, если работа потеряется?**

| Механизм | Когда применять | Потеря при рестарте |
| --- | --- | --- |
| Background tasks | Best-effort работа внутри одного запроса | Допустима |
| **Durable outbox** | Одноразовая работа, которую нельзя потерять | Недопустима |
| Jobs registry | Работа по расписанию, независимо от запросов | Не применимо |

**Durable outbox** — строка в PostgreSQL с ключом дедупликации, fencing-токеном, арендой и счётчиком попыток. Задача забирается воркером, ретраится до успеха или до отказа. В MVP через outbox идут: генерация брифа, генерация черновика, публикация статьи и последующая инвалидация CDN.

**Jobs registry** — одно объявление задачи, три взаимозаменяемых исполнителя: одноразовый запуск по таймеру площадки, планировщик внутри долгоживущего процесса, и цикл-воркер. Задача говорит *что* делать и никогда — *когда* и *где*.

## 6. Правило добавления инфраструктуры

**Реши задачу той инфраструктурой, которая уже есть, прежде чем добавлять новую.** Стартовый набор: PostgreSQL, один backend-процесс, реестр фоновых задач.

Очередь, брокер, кеш, поисковый движок — это не библиотека. Это то, что нужно развернуть, мониторить, защищать, бэкапить и оплачивать, и новый способ сломать продукт при здоровой базе.

У каждого из них есть меньший первый ответ внутри того, что уже есть:

| Соблазн | Первый ответ |
| --- | --- |
| Очередь как сервис | Строка в outbox, забираемая задачей дренажа |
| Кеш | Индекс или более узкий запрос |
| Поисковый движок | Полнотекстовый поиск PostgreSQL |
| Векторная база | `pgvector` в той же базе |
| Брокер для межпроцессных уведомлений | Строка и опрос |
| Внешний оркестратор (n8n) | Модуль внутри монолита |

Это не абсолютный запрет. Компонент добавляется, когда достигнут **измеренный** предел текущего подхода и новый компонент этот предел снимает: дренаж не успевает на минимальном интервале и очередь растёт от запуска к запуску; доставка нужна процессам, не разделяющим эту базу; работе нужны гарантии порядка или exactly-once, которых PostgreSQL не выражает.

**Измерение записывается в [CHECKLIST.md](../CHECKLIST.md) рядом со строкой возможности — до добавления компонента.** Это то, что позволит будущей сессии отличить реальный предел от вкусового предпочтения.

Не вводим: микросервисы, Kubernetes, Redis, Valkey, Kafka, RabbitMQ, Elasticsearch, n8n.

## 7. Машинно-проверяемые границы

Правила ниже реализуются в `scripts/architecture-check.mjs` (Wave 2) и проверяются в CI. Нарушение — падение с указанием `path:line`. У каждого правила есть фикстурные тесты.

| Правило | Содержание |
| --- | --- |
| **AC-1** | SDK провайдеров и внешние HTTP-клиенты допустимы только внутри `backend/src/providers/**` |
| **AC-2** | `backend/src/providers/llm/**` не импортирует `modules/leads/**`, `modules/attribution/**` и другие модули персональных данных |
| **AC-3** | В репозитории нет Telegram-автоматизации аккаунтов, MTProto, массовых приглашений и пакетов исходящей рассылки |

Дополнительно проверяются унаследованные из шаблона границы слоёв: `transport/` без Prisma, `application/` и `domain/` без Hono, Prisma, env и SDK, `packages/contracts` без импортов из поверхностей.

**Почему это правила сборки, а не соглашения.** AC-2 — единственное, что технически удерживает персональные данные от попадания к LLM-провайдеру. Соглашение здесь ломается первым же рефакторингом, который «просто передал объект целиком».

## 8. Данные

- PostgreSQL — единственное хранилище состояния.
- Prisma — источник правды схемы. Миграции генерируются из схемы; SQL руками не пишется.
- Первичные ключи — UUIDv7 с нативным типом колонки `uuid`. Где происходит генерация — открытый вопрос, см. [DEPLOYMENT.md](DEPLOYMENT.md).
- `pgvector` — для эмбеддингов кластеризации, в той же базе.
- Закрытый набор значений — enum PostgreSQL. Открытый — текстовая колонка, валидируемая в коде против реестра. Так добавление типа задачи или цели публикации остаётся изменением кода, а не необратимым `ALTER TYPE`.
- Все продуктовые таблицы несут `workspace_id` с первого дня. Логики изоляции в MVP нет; добавить колонку позже несопоставимо дороже, чем нести её сейчас.

## 9. Frontend

Две браузерные поверхности, разделённые по одному признаку — нужен ли странице SEO.

- **`website`** (Astro, SSG) — публичные, индексируемые страницы: продуктовые страницы четырёх линий услуг, статьи, кластеры, региональные страницы, политики, CTA-формы.
- **`webapp`** (React, CSR) — всё за авторизацией: заявки, исследование, редактор, очередь одобрения, публикации, лиды, воронка, `/admin/*`.

Правила `webapp`: серверным состоянием владеет слой server-state, состоянием форм — слой форм, схемы приходят только из `packages/contracts`. `src/components/ui` и платформенный слой никогда не импортируют продуктовые фичи; кросс-фича — только через публичный индекс фичи.

SEO-критичное содержимое должно присутствовать в исходном HTML: title, description, canonical, теги превью, заголовки и описания. Клиентские скрипты могут дополнять страницу, но не могут быть единственным источником SEO-критичного содержимого.

Подробности разделения — в [WEB_SURFACES.md](WEB_SURFACES.md).

## 10. Авторизация

- Пароли — Argon2id.
- Access-токены — короткоживущие JWT.
- Refresh-токены — непрозрачные; в базе хранятся только хеши текущего и непосредственно предыдущего. Ротация атомарна, повтор старого токена вне узкого окна гонки трактуется как компрометация и отзывает сессию.
- Роли — `admin | editor | viewer` — **не кладутся в JWT**. Каждый аутентифицированный запрос резолвит пользователя через активную сессию в базе, поэтому изменение прав действует немедленно.
- Состояние «ноль администраторов» запрещено сериализуемой транзакцией.
- Cookie-стратегия и CORS — в [DOMAINS.md](DOMAINS.md).

## 11. Что архитектура делает невозможным

Часть требований продукта выражена не документацией, а тем, чего в системе нет или что запрещено схемой:

| Требование | Как обеспечено |
| --- | --- |
| Нельзя опубликовать без одобрения | `publications.approval_id NOT NULL` + внешний ключ |
| Одобрение нельзя обойти правкой после факта | Одобрение привязано к content hash; изменение текста аннулирует его |
| Персональные данные не попадут в LLM | Правило AC-2 + runtime-guard на `LlmPort` |
| Нельзя случайно начать рассылку | Адаптера отправки нет; правило AC-3 не даёт добавить зависимость |
| Нельзя запустить продакшн со сломанным комплаенсом | `env.ts` отказывается поднимать процесс при расхождении предохранителей с фазой |
