# GEO-волна: факты, вопросы и видимость

Расширение SEO-конвейера для генеративного поиска (GEO) — не «хак» поверх существующего
среза, а отдельная волна с собственными сущностями. Порядок шагов — раздел «Что будет
реализовано дальше» в [README.md](../README.md), шаг 5.

**Статус: в работе.** Юнит 1 (реестр фактов) реализован; остальные юниты описаны ниже и
начинаются по мере готовности.

---

## 1. Принципы волны

1. **Факты — раньше текстов.** Ни один материал не может утверждать то, чего нет в
   реестре подтверждённых фактов. Реестр заполняет человек, проверяя источник.
2. **Никакой массовой генерации страниц.** Ответные ассеты создаются под конкретные
   вопросы из инвентаря, по одному, через обычный конвейер одобрения.
3. **Никаких манипуляций моделями.** Снимки видимости снимаются вручную в реальных
   интерфейсах поисковиков; ничто не оптимизирует контент «под выдачу» обходным путём.
4. **Граница ПДн не меняется.** LLM получает ключевые запросы, структуру брифа, текст
   статьи и текст подтверждённых claims — и ничего больше. Правило AC-2 продолжает
   действовать на модуль провайдера.

## 2. Юниты

| Юнит | Содержимое | Статус |
| --- | --- | --- |
| 1 | **Реестр подтверждённых фактов**: `EvidenceSource`, `Claim`, `Citation`; верификация человеком; коррекция через supersede; экран «Факты» в webapp | ✅ реализован |
| 2 | **Вопросный инвентарь `GEOQuery`**: вопросы реальных пользователей и машинных диалогов по кластерам и регионам; триаж open → planned → answered, отклонение с причиной; экран «GEO» в webapp | ✅ реализован |
| 3 | **Ручные снимки `GEOVisibilitySnapshot`**: вручную снятые результаты по GEO-запросам (упоминается ли бренд, какая позиция, какая формулировка), серия снимков во времени; секция на экране «GEO» | ✅ реализован |
| 4 | **Ответные ассеты с цитатами**: материалы, построенные на подтверждённых claims; каждая claim в ассете обязана ссылаться на `Claim` → `Citation` → `EvidenceSource`; одобрение через общий approvals-gate, привязанный к content hash; при одобрении вопрос переходит в answered | ✅ реализован |

Каждый юнит проходит обычный протокол: контракты → backend → поверхности → тесты →
зелёная цепочка проверок до передачи.

## 3. Юнит 1 — реестр подтверждённых фактов

### 3.1. Сущности

| Сущность | Что это | Ключевые правила |
| --- | --- | --- |
| `EvidenceSource` | Источник, проверенный человеком: ГОСТ/ТУ, документ производителя, регламент, прайс, отраслевая публикация | Пригоден после верификации (`verified_at` + `verified_by_id`); создатель и верификатор записываются раздельно |
| `Claim` | Утверждение о факте на русском, извлечённое из источника | Строки неизменяемы; коррекция — новый claim, связанный через `superseded_by_id`; дедупликация по SHA-256 утверждения в рамках источника |
| `Citation` | Место в источнике, где факт подтверждён: раздел/страница/таблица + короткая цитата | Человек может найти факт снова; цитата не содержит персональных данных |

### 3.2. Правило пригодности

Content может использовать claim только если он **верифицирован человеком и не
суперседнут**. Предикат — `isUsableClaim` в
`backend/src/modules/evidence/domain/evidence.ts`; интеграция с конвейером (использование
claims при генерации драфтов и в ответных ассетах) — в следующих юнитах.

### 3.3. Права

Чтение — любой авторизованный; создание, верификация, суперсед — `admin`/`editor`.

### 3.4. Роли записи

- `POST /api/evidence/sources`, `POST /api/evidence/sources/:id/verify`, `GET /api/evidence/sources`
- `POST /api/evidence/claims`, `POST /api/evidence/claims/:id/verify`, `POST /api/evidence/claims/:id/supersede`, `GET /api/evidence/claims`

Контракты — `packages/contracts/src/evidence.ts`. Тесты: контрактные, интеграционные
(`backend/tests/integration/evidence.integration.test.ts`), доменные правила в модуле.

## 3.5. Юнит 2 — вопросный инвентарь

| Сущность | Что это | Ключевые правила |
| --- | --- | --- |
| `GeoQuery` | Вопрос реального пользователя или машинного диалога, записанный человеком | Приоритет low/medium/high; жизненный цикл open → planned → answered; отклонение возможно на любом шаге триажа, терминально и только с причиной |

- Роли: `POST /api/geo/queries`, `PATCH /api/geo/queries/:id`, `GET /api/geo/queries`.
- Терминальные состояния `answered` и `dismissed` заморожены — переходы проверяются в
  домене (`backend/src/modules/geo/domain/geo.ts`) и в тестах.
- Ответные ассеты (юнит 4) будут строиться на `planned`-вопросах и переводить их в
  `answered`; связка появится в этом юните, не раньше.

## 3.6. Юнит 3 — снимки видимости

| Сущность | Что это | Ключевые правила |
| --- | --- | --- |
| `GeoVisibilitySnapshot` | Запись того, что человек увидел в реальном интерфейсе поисковика или ассистента по вопросу из инвентаря | Append-only: каждый снимок — новая строка, серия во времени — сигнал видимости; снимается только для `open`/`planned` вопросов; `answered`/`dismissed` заморожены |

- Роли: `POST /api/geo/queries/:id/snapshots`, `GET /api/geo/queries/:id/snapshots`.
- Ничего не парсится и не автоматизируется: снимок снимает человек, в интерфейсе,
  по реальному вопросу; поле `searchEngine` — открытое множество, валидируемое в коде.
- `mentionPosition` допускается только когда бренд упомянут — правило в контракте.

## 3.7. Юнит 4 — ответные ассеты

| Сущность | Что это | Ключевые правила |
| --- | --- | --- |
| `GeoAnswerAsset` | Ответный материал для одного вопроса из инвентаря, написанный и проверенный человеком | Создаётся только для `planned`-вопроса, один на вопрос; каждый связанный claim должен быть верифицирован и не суперседнут — на сохранении и на одобрении |

- Одобрение идёт через **общий approvals-контекст** (`subject_type = geo_answer_asset`),
  привязанный к content hash ассета: правка тела или набора claims меняет hash и
  отсоединяет одобрение — то же правило, что для планов, ревизий и публикаций.
  Отдельной «модели одобрения» для GEO нет и не будет.
- При одобрении вопрос автоматически переходит `planned → answered`.
- После одобрения claim может быть суперседнут — ассет остаётся читаемым, связка
  видна в UI; пере-одобрение с суперседнутым claim'ом отклоняется.
- Роли: `POST /api/geo/queries/:id/answer`, `PATCH /api/geo/answers/:id`,
  `GET /api/geo/answers`; одобрение — `POST /api/geo/answers/:id/approve` для `admin`.
- Генерация текста ассетов моделью — за пределами этого юнита: если появится, то
  через существующий конвейер контент-фабрики, а не новым обходным путём.

---

## 4. Чего волна не делает

- не генерирует страницы под каждый возможный вопрос заранее;
- не парсит выдачу поисковиков автоматически — снимки ручные;
- не оптимизирует промпты «под ответы моделей» — контент пишется для людей и фактов;
- не трогает модель одобрения: ответные ассеты публикуются только через approvals,
  привязанные к content hash.
